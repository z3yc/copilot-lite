# 引用溯源（R3/M5）四连复盘：跳错地方、跳不到文件、正文点不动、编号错位

> 日期：2026-09-16 ｜ 分支：`feat/rag-citation-source`（R3 主体）+ `fix/citation-jump-target`（R3.1/R3.2 修复）
> 起因：**人工核验**（不是测试报告）暴露的三个问题——① 点引用"只能跳到知识库，到不了具体哪个文件"；② 模型正文里的 `[n]` 与"来源："清单是纯文本、点不动；③ 模型引到 `[8]`，系统里只有 5 条引用。
> 结果：挖出**四个独立根因**（一个展示口径问题、一个前端跳转前置条件错误、一个类型降级错误、一个后端编号覆盖），全部修复 + 真机重启验证。
> 关联：`docs/优化落地记录.md` 第十六/十七节（R3、R3.1、R3.2）· `docs/plans/2026-09-15-r3-citation-source.md`（设计与实施计划）· `OPTIMIZATION_PLAN.md` §12

## 0. 一句话（面试开场用）

> 用户报的是"引用点不动/跳不到"，我没有直接去改点击事件，而是先**查库取证**：读 `extra.citations` 与 `extra.tool_calls`，发现这一轮 `kb_search` 被调了 **2 次**、两次都从 `[1]` 开始编号且**覆盖**写入，而模型正文写到 `[8]` —— 也就是说**点不动只是表象，编号在数据层就已经错了**。再往前一层，前端把"目标出现在列表里"当成了打开详情的前置条件（列表只有第一页 20 条），并且 Wiki 引用在丢失页面身份时会**降级**成"跳文档"。四个根因分四刀修，每一刀都先复现再改。

## 1. 用户视角的现象（三个，其实是四层问题）

| # | 现象 | 表面归因（错） | 真实根因 |
|---|---|---|---|
| A | 点引用 → 只切到"知识库"，看不到那份文件 | "跳转事件没绑上/前端没实现" | 跳转**落点**依赖"目标在第一页列表里"（`fetchDocs` 只取 20 条） |
| B | Wiki 引用也跳到知识库 | "Wiki 跳转没写" | 引用**类型降级**：`wiki.page_id` 缺失时回退到"跳文档"（而 wiki chunk 的 `document_id` 恒存在，所以必然发生） |
| C | 回答正文里的 `[1]`、模型自写的"来源："清单点不动 | "模型输出没办法做成链接" | 正文 `[n]` 是纯 Markdown 文本；只有"来源行"那排 `[n]` 是链接 |
| D | 模型引到 `[8]`，库里只有 5 条 citation | "模型幻觉" | 同轮多次 `kb_search`，每次从 1 编号 **且覆盖** `ctx.citations` |

> 教训先摆这里：**A 与 D 都是"数据/结构错了，却在交互层表现"**。只改交互（加个 onClick）会得到一个"点了确实跑到知识库、但打开的仍然是错文档"的版本——看起来修好了，实际更糟。

## 2. 排查过程（方法论，面试重点）

### 2.1 第一步：先取证，再动代码

用户贴出来的是一串文本：`[1] 📥 收件箱 | [2] 🎯 项目 | … | [8] 🏠 首页 > 命名规范`。第一件事不是改代码，而是判断**这串东西到底是哪个环节产出的**：

1. 来源行（组件渲染）长什么样？→ 只渲染 `[n]`（标题在 `title` 属性里），且 `.cite` 是下划线主色 → **不是链接样式的问题**；
2. 那就查库，看这条消息到底存了什么：

```python
# 直接读 messages 表（一次性诊断脚本，跑完即删）
select created_at, content, extra from messages
where role='assistant' and extra is not null order by created_at desc limit 8
```

结果（决定性）：
- 该回答**正文第 56 行**就是 `**来源**：[1] 📥 收件箱 | [2] 🎯 项目 | … | [8] 🏠 首页 > 命名规范` → 用户贴的是**模型写进正文的内容**，不是我们的来源行；
- `extra.citations` 只有 **5** 条，且**都是 R3 之前的旧格式**（`source_kind` 缺失、无 `wiki`），但 `document_id` 齐全、文档也都**没被删除**；
- 说明"点不动"与"文档不存在"无关。

### 2.2 第二步：数工具调用次数（一步定位 D）

```python
tool_calls = extra["tool_calls"]      # → 2 条，都是 kb_search
# 两次 payload 的「编号」都从 1 开始
```

模型嘴上 `[1]…[8]`，系统里 `5` 条 → **编号对不上**。到这里 D 已经闭环：`kb_tool` 每次 `ctx.citations = citations` 是**覆盖**写，不是追加。

### 2.3 第三步：用探针测试证明 A（而不是"看代码觉得是"）

对 A 我写了一个**临时探针用例**（跑完即删，不进仓库）：让 `fetchDocs` 只返回 `d1`，而 `openTarget` 指向 `d2`：

```tsx
render(<KbPanel openTarget={{ docId: "d2" }} … />);
await waitFor(() => expect(mocked.fetchDocDetail).toHaveBeenCalled());
```

结果 **`fetchDocDetail` 一次都没被调用** —— 这比"读代码发现有个 early return"强得多，因为它同时证明了"分页/过滤会把目标挡在列表外"和"挡在列表外时静默失败（不报错）"。

### 2.4 第四步：把判据收敛到一处（顺手消除"分叉"）

排查中发现**同一个决策写了两份**：

```tsx
// ChatPanel：决定 [n] 能不能点
const navigable = !!(c.wiki?.page_id || c.document_id);
// App：决定点了去哪
if (c.wiki?.page_id) {…} else if (c.document_id) {…}
```

两份判据在"wiki 缺 page_id"这一格上**结论相反**（ChatPanel 说能点，App 说跳文档）→ 用户看到的就是"点了，跳到知识库"。修法：抽 `resolveCitationTarget(c)` 纯函数做**唯一判据**，两个组件共用。这不只是去重，而是把"降级策略"变成了**可被单测锁住的一条规则**。

## 3. 四个根因与修法（含取舍）

| # | 根因（机制层） | 修法 | 取舍/代价 |
|---|---|---|---|
| A | 落点以"目标出现在当前列表"为前置条件；列表只有第一页 20 条且被分类/搜索过滤 | `KbPanel` 收到目标就**按 id 直接拉详情**；目标不在列表时渲染**独立「引用来源」卡片** | 需要抽出共用的 `DocDetailBody`，否则内联/独立两处 JSX 分叉 |
| B | `source_kind==="wiki"` 但缺 `page_id` 时**降级**为文档跳转 | `resolveCitationTarget`：wiki 缺身份 → 返回 `null`（**不可点**，悬停提示"页面已删除或暂不可用"）；旧格式（无 `source_kind`）仍按 `document_id` 尽力跳 | 页面被软删的旧消息会"不可点"而不是"跳到可能相关的文档"——**宁可不可点，也不跳错地方** |
| C | 正文 `[n]` 是纯文本 | `linkifyCitations(md, indexes)`：把 `[n]` 转成 `[[n]](#cite-n)`（保留方括号外观），`ChatPanel` 事件委托拦截 → 复用同一个 `activateCitation` | ① 只对有对应引用的编号转（**不做死链**）② 行内代码/围栏代码块内不转 ③ 流式期间 citations 还没到 → 回答完成那刻才变链接 |
| D | 每次 `kb_search` 从 1 编号 + `ctx.citations = …` 覆盖 | `offset = len(ctx.citations)`：编号**跨调用连续**，citations **追加**（`[*old, *new]`），payload「编号」同步用全局编号 | 同一轮里重复搜同一个词会重复登记（可用 index 去重，当前不做——编号稳定比去重更重要） |

**一个设计判断值得单独讲**：C 的关键不是"把文本变链接"，而是**"只在有对应引用时才变"**。否则模型随手编的 `[9]` 会变成一条通向"不存在/错来源"的死链——那比纯文本更糟：用户点一次就不再信任引用。

## 5. 这次踩到的坑（含我自己写下的坑）

1. **"改了代码没生效"是环境问题**：原来跑的后端不是 venv，而是 `WindowsApps\…\python.exe -m uvicorn …`，并且**没有 `--reload`**——任何代码改动都不会加载。**自证方式**：拿"进程启动时间"与"文件 mtime"比大小，再看 Vite 转译产物里有没有新符号；不要用"我觉得应该生效了"。
2. **前端 `loadPages` 被 `onClick={loadPages}` 直接引用**：为支持"切空间后立刻拉新空间的页"把参数改成可选后，React 会把**鼠标事件**当参数传进去（`tsc` 直接报 `MouseEventHandler` 不兼容）。修法：`onClick={() => loadPages()}` + `typeof spaceId === "string"` 守卫。
3. **详情渲染挂在列表卡片内部**（`expandedId === d.id && …`）：所以"按 id 打开详情"必须先让目标出现在列表里——这正是 A 的由来。**这是我 R3 时自己写下的错误设计**：把"跳转"实现成了"查询副产品"。
4. **测试断言要挑可见元素**：分块正文在 `Collapse` 里默认收起，断言正文文本必挂；改断言分块标签 `#0`（同时也锁住了"确实展开了"）。
5. **测试夹具的 `document_id` 必须合法**：探针里写 `document_id="dX"`，触发了"双链邻居扩展"里对 UUID 的解析 → 报 `badly formed hexadecimal UUID string`，一开始误以为是新代码坏了。
6. **`docs/` 在 `private-docs` 分支被 `.gitignore` 忽略**（历史遗留的"本地文档"策略），新增计划文档要 `git add -f`；而 `面试准备/` 未被忽略，普通 `add` 即可。
7. **连接器注册表不在 `registry.py`**：`_REGISTRY`/`register_connector` 都在 `app/connectors/base.py`，实施计划里假设的文件不存在 → 按现状落位（并把新函数一并放那里 + 补 `__init__` 导出）。
8. **提交粒度会被编译约束倒逼**：App 同时给两个面板传新 prop 会让另一个面板 `tsc` 报错 → 把"App→Wiki"与"App→Kb"拆成两个提交，保证**每个提交都能 build**。

## 6. 面试问答（预演）

**Q：引用"类型区分"你怎么做的？为什么不用重建索引？**
A：标签格式收敛在一个纯函数里（`Wiki / 空间 / 页面` 与 `文档 / 文件名 / 标题路径 / 第 N 页`），**身份解析**收敛到连接器 seam（`SourceConnector.describe_sources()` 可选实现）。Wiki 页面身份用**查询期一次 `WikiPage JOIN WikiSpace`** 拿，所以存量 chunk 不必重导、也不必重建向量索引；连接器挂了只降级标签（用 chunk meta 兜底），不拖垮检索。

**Q：用户说"点引用跳不到文件"，你怎么定位？**
A：先证伪两个容易误判的方向——① 文档是不是被删了（查库：没删）；② 是不是点击事件没绑（查组件渲染：`.cite` 是带下划线的链接）。然后写**探针用例**证明机制：让列表里没有目标文档，断言 `fetchDocDetail` 有没有被调用 —— 结果一次都没有。根因就是 `if (!docs.some(...)) return;` 把"目标在列表里"当成了前置条件，而列表只有第一页 20 条。

**Q：修法是？有没有更简单的选择？**
A：点击就**按 id 直接取详情并按 id 渲染**——列表只是旁证，不是前置条件；目标不在列表时渲染一张独立的「引用来源」卡片。更简单的做法是"把 page_size 调到 100"，但那是把分页问题藏起来：文档超过 100 条、或者用户当前用了分类/搜索过滤，问题会以同样的形式回来。

**Q：为什么 Wiki 引用缺了身份不能"退一步跳文档"？**
A：因为 wiki chunk 的 `document_id` 恒存在，这个"退一步"**必然触发**，结果是把用户带到知识库里另一份（可能相关的）文档——**看起来像跳了，实际到了错的地方**。降级应该往"不跳"走：不可点 + 悬停说明"页面已删除或暂不可用"。这条我写成了单测锁死（wiki 缺 `page_id` 必须返回 `null`）。

**Q：模型正文里的 `[n]` 怎么做成可点的？**
A：`linkifyCitations()` 在渲染前把 `[n]` 转成 `[[n]](#cite-n)`，组件里用事件委托拦截 `a[href^="#cite-"]` 并 `preventDefault`。三条约束：只在**有对应引用**时转（不做死链）、**代码块/行内代码不转**（否则往代码里插链接）、已有的 Markdown 链接 `[1](url)` 不动。用原生 `<a>` 而不是 `<span role="button">`，键盘可达性就白拿。

**Q：为什么会有"编号错位"这种问题？**
A：因为**一轮里工具可能被调用多次**（模型换个措辞再搜一次是很常见的），而实现里每次调用都从 `[1]` 开始编号、并且 `ctx.citations = citations` 是**覆盖**写。模型正文写 `[8]`，系统里只有 5 条 —— 前端做多少交互都是错的。修法是一行级别的语义修正：`offset = len(ctx.citations)`，编号一轮内**单调累加**、引用**追加**。这类问题的本质是"**编号是跨调用共享的状态**，实现时被当成了每次调用的局部量"。

**Q：怎么防止"点得动"这件事回归？**
A：把判据收敛成**一个纯函数**（`resolveCitationTarget`），它是唯一出口，前端两个组件共用；再为每一格可能的状态写单测（wiki 带身份/缺身份、旧格式、无目标、无 space_id）。之前正是"两个组件各写一份判据"导致结论相反——**分叉的判据等于没有判据**。

**Q：这次最值得复用的经验是什么？**
A：**"用户报的是交互，根因常在数据"**。这次三个现象（跳不到文件、点不动、编号错位）分别在"列表分页依赖""文本渲染""工具调用编号"三处，但都是**同一个能力链路上的结构问题**：引用要能溯源，前提是①编号唯一稳定 ②身份可解析 ③落点不依赖旁路条件。我按这个顺序查，比从交互层往上猜快得多。

## 7. 残留与边界（主动交代）

- **历史消息不重算**：`extra.citations` 已落库，旧消息里模型写到的 `[6][7][8]` 仍然不可点（需重新提问才生效）——这是有意的选择（不重算历史），但也意味着"修复不可回溯"。
- **模型编造的编号永远是纯文本**：宁可不可点，也不指向错来源。
- **流式期间不可点**：citations 在 `done` 事件才送达，正文 `[n]` 在回答完成那一刻才变链接；若要流式期间就可点，需要提前下发"已产出引用"事件（属独立改动）。
- **wiki 引用缺身份时变得"不可点"**：属于刻意的降级方向，但用户体验上是"少了功能而不是跳错"，需要在 UI 文案上说清。
- **未做去重**：同一轮重复检索同一内容会重复登记引用（编号稳定优先）。
- **合并待批准**：`feat/rag-citation-source`（6 提交）+ `fix/citation-jump-target`（4 提交）按 §11 需要维护者明确批准后再合入 `develop`。

## 8. 一句话总结（收尾用）

> 这次最值钱的不是"让引用能点"，而是**把"能点"拆成了三个可验证的前提**——编号唯一稳定（后端编号累加）、身份可解析（连接器 seam + 查询期 JOIN）、落点不依赖旁路条件（按 id 直开、列表只是旁证）；三个前提各自有单测锁住，再叠加真机重启验证（进程启动时间 vs 文件 mtime 证明加载的是新代码）。引用溯源做对了，是"每条结论都能指回原文"；做错了，就是"点一下，跳到知识库里某个不相干的地方"。
