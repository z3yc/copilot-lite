# 流式回答被静默截断 / 工具轮独白泄漏 / 新会话首条自杀 —— 一次三连根因复盘

> 日期：2026-09-15 ｜ 分支：`fix/stream-truncation`（tip `21abe5d`，自 `develop` `8d79c11` 切出）
> 起因：**真实使用**（不是测试报告）中发起一次 wiki 提问，得到两条错误现象：开头弹 `生成出错：已停止生成`；助手回复变成英文且「只说要做、不去做」。
> 结果：一次排查挖出**三个独立根因**（一个深层 asyncio 机制、一个被打破的模型行为假设、一个 React effect 语义陷阱），全部修复并真机验证。
> 关联：`docs/优化落地记录.md` 第十五节（R2.1）· `docs/plans/2026-09-15-stream-fixes.md`（实施计划）· `OPTIMIZATION_PLAN.md` §12

## 0. 一句话（面试开场用）

> 用户只报了「回复变成英文、还报了个停止」两个现象；我没有直接改表象，而是先做**受控复现 + 同进程对比**，定位出三个各自独立、且**都不是这个功能引入**的根因：`asyncio.wait_for` 在超时时会**取消** `anext()` 从而**静默终止异步生成器**（导致回答被截断却仍发 `done`）；模型在工具调用轮**同时输出 content**（打破了代码里写死的「content 与 tool_calls 互斥」假设）；以及一个「React effect 依赖没变就不会重跑」导致新会话首条消息取消自己。修复后真机复现原来坏掉的那条路径：**21.15 秒静默、心跳照发、答案完整、无独白、流式与落库逐字节相等。**

## 1. 用户视角的三个现象

| # | 现象 | 真实严重度 |
|---|---|---|
| A | 新会话第一条消息立刻 `生成出错：已停止生成` | 演示首屏就翻车 |
| B | 助手回复是英文独白（`I'll search the knowledge base …`），问题没被回答 | 看起来「模型变笨了」 |
| C | 长问题（wiki 检索）回答只剩半截 | **最严重：用户拿到残答案，系统却报成功** |

> 关键判断：**B 不是「模型变笨」，而是截断的副产物**——真实答案还没来得及生成，流就被掐断了，只剩下生成前的独白。先把三者当成一个现象会走偏，必须拆开。

## 2. 排查过程（面试重点：方法论，不是结论）

### 2.1 第一步：先看日志与落库，别猜

日志显示**工具其实被调用了**（`kb_search` 调了两次，每次还触发 3 路查询改写）。所以问题不在工具，在**给用户看的文本**。于是直接查 `messages` 表里到底存了什么：

```
14:45:40 assistant len=56  = "I'll search your knowledge base to see what's available."
14:46:18 assistant len=173 = "I'll search the knowledge base — but I need a topic…Let me try a broad search…"
```

**落库正文就是那句英文独白**，不是「独白 + 答案」。→ 现象 B 的本质是**没有答案**，不是语言问题。

### 2.2 第二步：同进程对比法（一次就锁定方向）

同一时刻、同一个后端进程，分别发**非流式**和**流式**请求同一问题：

| 路径 | `Message.extra.trajectory` | 落库正文 |
|---|---|---|
| 非流式 `/chat` | ✅ | `你的待办列表如下：…`（430 字，纯中文答案） |
| 流式 `/chat/stream` | ❌ | `I'll check your todo list for you.你的待办列表如下：…` |

**「同一进程内非流式正常、流式异常」** → 差异只可能在**流式专属的那段代码**里。这一步把搜索空间从「整个对话链路」缩到「流循环」，是本次最省时间的一步。

### 2.3 第三步：找第二条独立证人（交叉验证）

轨迹缺失其实有两条**互不相干的**证据链——`citations` 也一起没了：

- `citations` 在工具执行时写进 `ToolContext`，轨迹在收尾时 `build()`；
- 但**两者都只在 `run_stream` 的同一段收尾代码里被拷到实例属性上**（`self.last_citations = …` / `self.last_trajectory = …`）；
- 结果 `extra` 里只剩 `tool_calls`——而 `tool_calls` 是**工具执行时就地追加**的，不依赖收尾。

→ **收尾代码根本没执行**。这一条比轨迹本身更有力：它排除「轨迹功能坏了」，指向「流没跑完」。

### 2.4 第四步：对齐时间线，锁定心跳

日志时间线：长达 **14–21 秒**的区间里**没有任何模型输出 chunk**（工具轮模型在检索，不产文本），而 `chat.py` 里写着：

```python
_HEARTBEAT_SECONDS = 15.0
text = await asyncio.wait_for(anext(agent_stream), timeout=_HEARTBEAT_SECONDS)
except StopAsyncIteration: break
except TimeoutError:
    yield ": ping\n\n"     # 发心跳保活
    continue
```

**根因**：`asyncio.wait_for` 超时时**会取消**它包裹的那个 `anext()` 协程。而取消 `anext()` 等价于**就地把异步生成器终止**（生成器在挂起点收到 `CancelledError` 后终结，`finally` 执行、之后不可再迭代）。于是：

```
超时 → wait_for 取消 anext → 生成器已死
     → continue 再 anext() → 抛 StopAsyncIteration
     → 被 `except StopAsyncIteration: break` 当成「流正常结束」
     → 走 else: 分支落库 + 发 done     ← 语义撒谎
```

**为什么静默期长就必现**：`kb_search` 一次调用要跑 3 路查询改写 + 向量 + BM25 + 精排，一轮轻松 >15s；而 `todo_list` 只花 4ms，所以「有时好有时坏」——不是随机，是**依赖工具耗时**。

### 2.5 第五步（顺带挖出的第二个根因）：独白为什么会被当成回答

修完心跳后真机复验，看到落库正文仍带英文前缀，才注意到**模型在 tool_calls 那一轮同时输出了 content**。而两个引擎的 `run_stream` 都把它当回答全量转发，且两个引擎的注释里都写着一句被当成事实的假设：

> 「工具调用轮 content 为空、纯文本轮 tool_calls 为空，**二者互斥**」

**这个假设被真实模型打破了。** 修法是**按模型轮缓冲**：该轮有 `tool_calls` 就丢弃该轮文本，没有才产出；对**不挂工具的 `chat_agent`** 保持逐字流式（那类轮次不可能有工具调用）。

### 2.6 第六步（现象 A）：React effect 的依赖语义陷阱

```tsx
useEffect(() => {
  setMessages(initialMessages);
  abortRef.current?.abort();      // 无条件取消
}, [initialMessages, sessionId]);
```

父组件传 `onSessionCreated={setSessionId}`：新会话首条消息发出后，SSE `session` 事件把 `sessionId` 从 `null` 变成新 id → **这个 effect 触发 → 取消掉刚刚发起的那条流**。新会话第一条必挂，之后（id 已稳定）就正常。

修法：拆成两个 effect，只在**真正切走会话**时取消。

**这里有个很值得讲的细节**：我最初让实现者加一个 `streamingRef` 布尔守卫，被**正确地驳回**了——因为该守卫在 `[sessionId]` effect 里，而当用户点「新建会话」时 `newSession` 会把 `sessionId` **再设成 `null`**，React 对同值 `setState` 会**跳过重渲染**，effect **根本不会重跑**，守卫写在那里等于没写。正确做法是在**真正会变化的那条依赖**（`initialMessages`，因为 `newSession` 会 `setMessages([])`）上补守卫。
> 可迁移的教训：**要在依赖真的会变的地方加守卫，而不是在语义上「更该在那里」的地方。**

## 3. 三个根因的修法（含取舍）

| 根因 | 修法 | 取舍（面试要主动讲） |
|---|---|---|
| 心跳取消生成器 | 把 `anext` 挂成**一个 Task 跨心跳存活**：`done, _ = await asyncio.wait({task}, timeout=…)`，超时只发 ping、**绝不取消**；另加 `_STREAM_MAX_SECONDS` **静默上限**，超限走 `error`（504）而非 `done` | 超时不再能兜底，必须自己加总量约束；上限只在心跳边界求值（是静默预算，不是墙钟上限） |
| 工具轮独白泄漏 | 按轮缓冲 + 只在无工具调的轮产出；`tool_calls` 字段缺失时 **fail-closed + WARNING**（宁可丢独白也不泄漏）；工具轮耗尽 `max_turns` 时用节点收尾文本兜底（不给空回复） | **工具型 agent 失去逐字流式**（改整段出现）；代价之二：中止/断开该轮会**整轮丢文本**（停止按钮在 kb/tools 答案轮拿不到部分文本） |
| 新会话自杀 | 拆 effect + `streamSessionRef` 记录「这条流属于哪个会话」，只在归属真的变了才取消；守卫补在会变的依赖上 | 新建会话窗口内中止会走 `AbortError`，可能在刚清空的列表里留一条错误气泡（残留待修） |

**另外两个「定语义」的改动比修 bug 更值钱：**

1. **`done` 必须诚实**：`done` = 「整轮回答已完整产出并落库」。任何截断路径都必须走 `error`。这条一立，第 2.4 步那个「静默成功」就不再可能。
2. **对第三方 payload 的假设一律 fail-closed + 告警**：判断「这一轮有没有工具调用」依赖 LangChain `on_chat_model_end` 的 `output.tool_calls`。这个假设**今天成立**，但同一次排查已经证明「写死在注释里的假设会被打破」，所以字段缺失时**丢弃文本并告警**，而不是默认当成回答轮——否则将来会**静默重新泄漏**（不报错）。评审的原话是：*「a payload change would silently reproduce the original bug rather than error」*。

## 4. 验证（面试重点：怎么证明修好了）

| 手段 | 内容 | 为什么需要 |
|---|---|---|
| **受控复现** | 打**运行中的服务**（不是 in-process），复现出「落库只剩独白 + 无轨迹」 | Qdrant 本地模式有**文件锁**，服务在跑时无法进程内复现——踩过这个坑 |
| **防回归测试（先红后绿）** | 每条修复都有 RED → GREEN 证据；心跳那条的 RED 是 `回答被截断：[]` | 证明测试真的在测这个 bug |
| **变异测试自证非空转** | 把前端渲染临时改成 `dangerouslySetInnerHTML` → 断言必备挂；改回 → 通过 | 防止「断言写得看着对其实空转」 |
| **真机端到端** | 走**原本坏掉的那条慢路径**：`kb → kb_agent → kb_search → kb_search → answer`，**自然静默 21.15 秒**触发心跳，答案仍完整 1121 字、无英文独白、`extra` 同时含 `citations`+`tool_calls`+`trajectory`、**流式与落库逐字节相等（1121 == 1121）** | fake 与真实模型有保真度差异（见下），必须真机 |
| **僵尸进程自检** | 每个请求确认落在**我自己进程**的日志里 | Windows 上残留 worker 会占着端口继续跑旧代码，曾两次骗过我 |

> **fake 保真度这个坑必须讲**：`GenericFakeChatModel` 在**流式**下会**丢弃 `AIMessage.tool_calls`**，导致「工具根本不会被执行」，测试必须 override `_stream` 才能模拟。也就是说：**单测全绿不能证明流式下工具调用正常**——这正是必须在最后补一次真机验证的原因。

## 5. 我在这次排查里犯的两个测量错误（面试主动讲，体现严谨）

1. **把 `json` 列当成了字符串**：asyncpg 把 `extra` 以字符串返回，我写了 `'trajectory' in extra`，于是它变成了**子串匹配**；加上终端输出被截断（`trajectory` 恰好排在 `_build_extra` 的**末尾**），我一度得出「所有消息都没轨迹」的错误结论。改成严格 `json.loads` 后才看清真相是**流式丢、非流式不丢**——而这恰好是最有信息量的那个不对称。
2. **抓错了 SSE 帧**：我用「最后一条非空 `data`」判断 `done` 的 payload，结果抓到了 `chunk` 的 `{"text":"？"}`，于是误报「关闭开关后 `done` 仍带 trajectory」。改成**按事件名捕获**后，`done` 的 payload 确实是 `{}`。

> 教训：**测量本身要能被怀疑**。凡是「结论和预期一致」的地方，我都会再问一句「我这个测量会不会自己就错了」——这两次都是这么发现的。

## 6. 面试问答（预演）

**Q：你怎么定位到是心跳的问题？**
A：三步。① 先看落库正文，发现存的只是英文独白、没有答案，说明「没有答案」而不是「语言问题」；② 同一进程内非流式/流式对比，非流式完全正常——把范围缩到流式专属代码；③ 找第二条独立证人：`citations` 也一起丢了，而它和轨迹**都只在 `run_stream` 的同一段收尾代码里被拷贝**，说明收尾没执行，不是轨迹功能本身的问题。再看时间线，静默 14-21 秒 > 心跳 15 秒，就落到 `asyncio.wait_for` 上了。

**Q：`done` 说谎这件事你怎么防？**
A：我把 `done` 的语义**定义为「整轮回答已完整产出并落库」**并写成约束：任何截断路径必须走 `error`。这次静默上限触顶就返回 504 → 走 `error` + 保留部分落库。语义一立，「静默成功」在结构上就不可能了，而不是靠某处记得处理。

**Q：为什么超时会取消生成器？**
A：`asyncio.wait_for(coro, timeout)` 的超时实现是**取消它包裹的那个 future/coroutine**。而 `anext()` 被取消时，生成器在挂起点收到 `CancelledError` 就终结，之后不可再迭代——外部只看到 `StopAsyncIteration`，与「正常迭代结束」**无法区分**。这是最阴的地方：错误被伪装成正常结束。修法是把 `anext` 挂成一个 Task，用 `asyncio.wait({task}, timeout=…)` 等它——超时只返回「还没好」，不动那个 Task。

**Q：工具调用轮的独白怎么处理？代价是什么？**
A：按模型轮缓冲：有 `tool_calls` 的轮丢弃文本，没有的轮才产出。代价有两个，我都接受并写进了冻结候选：① 挂工具的 agent 失去逐字流式（答案整段出现），只有不挂工具的 `chat_agent` 保留逐字；② 中止/断开时该轮文本整轮丢失，所以「停止」按钮在 kb/tools 答案轮拿不到部分文本。要两者兼得就得新增一个 additive 的「替换正文」事件，那是一次独立改动，我没有塞进这次修复。

**Q：前端那个 bug 的根因是什么？**
A：一个 effect 的依赖里同时有 `initialMessages` 和 `sessionId`，并且无条件 `abort()`。首条消息发出后 SSE 返回新会话 id，父组件把 `sessionId` 从 `null` 改成新 id，effect 重跑就把**刚发起的请求取消**了。有个更深的点：我一开始想在 `[sessionId]` 这个 effect 里加守卫，但被驳回了——用户点「新建会话」时会把 `sessionId` **再设成 `null`**，React 对同值 setState 会跳过重渲染，那个 effect **根本不会重跑**。必须在依赖真的会变的地方（`initialMessages`）补守卫。

**Q：你如何保证测试不骗你？**
A：两件事。① 每条修复都要求**先红后绿**，并且用**变异测试**证明断言非空转（把正确的实现临时改坏，断言必须挂）。② 这次发现 `GenericFakeChatModel` 在流式下会丢 `tool_calls`——即**单测全绿并不能证明流式下工具调用正常**，所以最后一定补一次**真实模型端到端**，并且专门跑原来坏掉的那条慢路径。

**Q：如果重来一次，哪些设计会不一样？**
A：三件。① 流式链路加一条**「最大静默时长」可观测指标**——这次是靠读日志时间线人肉发现的，有指标就能提前告警；② `done` / `error` 这类**终态语义写进代码注释和测试**，不要只存在于实现者脑子里；③ 对第三方 payload 的假设要么**校验**要么 **fail-closed + 告警**，别写成注释里的「事实」——这次那句「content 与 tool_calls 互斥」就是被真实模型打破的。

## 7. 残留与边界（面试可主动交代，显成熟）

- **R1（同类残留）**：504 超时路径先 `cancel()` 再 `raise`，而 `except HTTPException` 直接落库、**从不 `await` 那个被取消的生产者**——与我修掉的 item 1 是**同一个共享 `AsyncSession` 竞态**，只是触发条件从「客户端断开」变成「静默上限」。现有 504 用例抓不到（fake 卡在 `asyncio.sleep` 而非 DB）。
- **R2**：新建会话窗口内中止会经 `AbortError` 分支，可能在刚清空的列表里留一条「生成出错」气泡。
- **已接受的取舍**：工具型 agent 不逐字流式；手写引擎整体不逐字流式（它每轮都可能调工具、无法预判）；`_STREAM_MAX_SECONDS` 仍是模块常量而非配置项（运维需可调时再提升）。
- **未取齐的规则**：`AGENTS.md` §11「禁止直接 push `develop`」与 `GIT_WORKFLOW.md`「正常推两个远端」互相矛盾，需择一改措辞——不然每次都只能靠一次性例外。

## 8. 一句话总结（收尾用）

> 这次最值钱的不是修了三个 bug，而是**「错误被伪装成正常结束」这一类问题的识别方式**：当系统报了成功、但用户拿到的东西不对时，先去查**收尾代码有没有执行**、再找**第二条独立证人**，往往能一步定位到机制层，而不是在表象上打补丁。
