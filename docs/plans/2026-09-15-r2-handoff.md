## 4. R2 有待决策的点（共 3 项，请在写计划前定）

**1. 手写 `Orchestrator` 是否也产出 trajectory？**
- Q0.2 把手写引擎定为**对照/回退**（功能冻结），但双引擎共享同一前端与同一 `Message.extra` 契约。
- **我的建议：也产出（同形状、成本低）**。理由：① 前端/落库契约不该随引擎分叉；② R5 的双引擎对照评测（token/延迟/准确率）需要两边都能回放；③ AGENTS §2 要求改动其一必须跑两套测试，若只有一边有轨迹，测试不对称。
- 代价：多写一份映射逻辑（ReAct 循环里记录 step 更简单）。

**2. trajectory 的体积与截断口径**
- `Message.extra` 是 JSON 列，全量落库可能让单条消息膨胀（多轮 + 长工具参数）。
- **我的建议**：落库前**规范化 + 上限**（例如最多 N 步、单步参数/结果各截断到 M 字符、超限记 `truncated: true`），并**禁落密钥**（§10.3）。

**3. 轨迹是否实时（流式）还是回答后一次性可见**
- 前端已有 SSE 事件通道；实时逐事件推送更亮但要改 SSE 契约（现有 `session/chunk/done`）。
- **我的建议：R2 只做"回答后可见"**（落库 + 前端展开面板），实时推送留给后续（符合 Q0.4「子 Agent 仅在上下文会被撑爆时引入」的克制口径）。
- 代价：Demo 镜头 2 的观感稍弱（点开才看到，而非实时滚动）。
