## 2. 原理：这轮到底在治什么病

### 2.1 四个结构性成因（不是"待办太多"）

| # | 病因 | 证据 | 为什么危险 |
|---|---|---|---|
| 1 | **backlog 背离验收标准** | 唯一未达成的红线（云上可演示）0%，路线图却把"当前主攻方向"标为批次 Q | 继续加功能不会让作品更可交付 |
| 2 | **不可验证 + 半成品更危险** | I1–I6 多租户在单用户环境测不出越权 | 半成品 ACL = 真实泄露面；面试被追问"怎么验证跨租户隔离"答不上来反而减分 |
| 3 | **计划自相矛盾** | `ADMIN_PLAN` §7 明写"企业能力只留缝不实现"，`OPTIMIZATION_PLAN` 却列 I1–I6 要"实现" | 待办虚胖，真交付项被淹没 |
| 4 | **计划文档双分支分叉** | `PLAN.md`/`OPTIMIZATION_PLAN.md` 在 `develop` 与 `private-docs` 各存一份，**md5 已不同** | 在一份上勾选、另一份还是旧的——沉积的技术成因 |

### 2.2 三个机制（可复用的部分）

1. **冻结 ≠ 删除，每条必须带重启条件**。没有重启条件的"暂缓"半年后一定会被重新当待办挖出来——这正是沉积的成因。例：`K2 新连接器` → 重启条件"出现真实数据源（如实习环境有 Confluence）"；`Q4 supervisor 深化` → "路由判错成为高频问题，**且有 trajectory 数据支撑**"。
2. **准入过滤器**（`DEMO_SCRIPT.md`）：新需求必须回答"进哪个镜头"或"讲出什么数据"，否则进冻结清单。把优先级判断从"感觉重要"变成"能否演示/能否度量"。
3. **单一进度事实来源**：进度只在 `OPTIMIZATION_PLAN.md` §13；`PLAN.md`/`ADMIN_PLAN.md` 为**镜像**并在文档里显式声明。任何"两处可勾同一交付物"都会漂移。

### 3.2 环境坑（Windows + GBK，会静默骗过你）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **控制台 GBK** | `grep`/`cat` 看中文：全角标点显示成半角、`❄️`/`🟡`/`░` 丢失 → 会**误判内容损坏**并白改一轮 | 核对中文**必须** Python 读文件 + `ascii()` 输出 |
| 2 | **`git filter-branch --msg-filter` 管道编码** | 传给 Python 的消息按控制台代码页解码 → 替换**静默失效**（不报错、内容看似没改） | 用 `sys.stdin.buffer`/`stdout.buffer` **字节级 UTF-8** 收发 |
| 3 | **CRLF/LF 差异** | 只改行尾的文件也显示 `M`，`git diff --stat` 却是空 | 用 `git diff --ignore-cr-at-eol` 判定"是否真的改了内容" |
| 4 | **生成文本标点风格漂移** | 我生成的正文半角标点占多数（27 全角 vs 182 半角），而仓库既有文档相反（`ADMIN_PLAN` 102 vs 18） | 确定性脚本归一（跳过代码围栏、保护行内代码、**嵌套括号要多轮扫描**） |

### 3.3 流程坑与有效做法

- **预检（pre-flight conflict scan）真的值钱**：派发前把"任务间共享文件/接口"和"任务自身文本 vs 自己给的预期值"逐条列成表，一次抓出 **4 处计划缺陷**（计数口径、溯源注记丢失、§14 陈旧、预期值错）。**带着已知错误派发 = 把错误传给实现者**。
- **同形小任务要批量派发**：`Task 3/4/5` 改同一文件且顺序耦合 → 合并成一次派发，避免彼此重复读取与冲突。
- **审查者要独立复现判据**：本次两次任务审查都亲自跑了计数命令，并**独立验证了实现者的声明**（例如"24 组条目"实际 25 行、`DEMO_SCRIPT.md` 与简报逐字节相等）。
- **子代理在 pi 里的实现**：`pi -p --no-session --no-skills --model <model>` = 独立进程 = 独立上下文；派发文案写成文件再 `$(cat)`，避免超长参数。
- **修复预算**：SDD 每任务 5 轮；Minor 不占预算（转 deferred 汇入最终修复波）；最终审查后**只有一次修复波 + 一次范围受限复审**。

### 3.4 新发现的矛盾（本轮已对齐）

`面试准备/Agent形态选型…md` 的 U4 原本写 **Task 实体「已定：要做」**，而 R0 的 §11 把 Q3 冻结 → 读者会以为 Q3 已放行并直接开工。**已改为：方向已定（要做）、排期未定（进冻结清单）**，并写明重启条件。**教训：冻结一个"方向已定"的东西，必须在原决策文档里同步改写它的状态词**，否则两份文档对同一件事给出相反指令。

## 6. 多智能体"趋势论"的讨论记录（重要）

**维护者观点**："多智能体是未来趋势。"

**我的回应（三点）**：

1. **R2 就是多智能体投资，不是绕开它**。trajectory 存在的唯一理由就是多智能体——"没有 trajectory 就不可调试、不可评测，先上形态不补可观测 = 自己把自己变成黑盒"。而且 **Q4（supervisor 深化）的重启条件本身就写着"要有 trajectory 数据支撑"**：R2 是仪器，Q4 是被仪器量出来的结论。
2. **面试场上"趋势"是最弱的论据**。面试官会追问："那你为什么不直接用单 agent + 多工具？多 agent 的错误传播和上下文碎片化怎么处理？有数据吗？"——**人人都知道趋势，很少人给出边界**。能加分的是反过来的说法：*"我做了双引擎对照，在 golden set 上比 token/延迟/准确率，发现 X 类问题收益明显、Y 类纯浪费，所以我的策略是……"* 这句话每个字都来自 **R2（轨迹）+ R5（双引擎对照）**，而 R5 已在路线图里。
3. **解冻要有证据，不是有信念**。Q2/Q3/Q4 的冻结条件全是经验性触发（工具数 > 15 / 出现跨轮跟进需求 / 路由判错高频 + 有轨迹数据）。**"未来趋势"不构成解冻条件**——但维护者若决定提前投入，作为维护者判断（明账写进文档），而不是偷偷当待办塞回去。

**结论（2026-09-15 定）**：**方案 A**——保持冻结；多智能体的"故事"由 **R2 轨迹 + R5 双引擎对照** 承担；等 R4 接了 MCP 工具数上来，Q2 会被自然触发；等自用中真出现跨轮跟进痛点，Q3 才有真实需求。**Q3 方向已定、排期未定**（已同步到《Agent 形态选型》U4）。
