## 逐项复盘记录

### C1 LLM 并发上限（`12437dd`）
- **改动**：config.py 加 `LLM_MAX_CONCURRENCY=3`；llm.py 模块级懒创建信号量 `_get_semaphore()`，非流式 `chat()` 用 `async with` 包裹，流式 `stream_chat` 在 finally 释放，`stream_raw` 返回 `_GuardedStream` 守卫迭代器（迭代耗尽/异常/取消时释放额度）
- **原理**：进程内信号量给所有模型调用设并发天花板——多个 SSE 同时提问时会各自触发 LLM 调用，无上限会打爆 API 限额并放大账单；流式请求生命周期长（几十秒），额度必须覆盖整个流并可靠归还
- **踩坑**：流式额度泄漏——如果只在 create 时拿锁、create 后立即释放，等于没限；所以守卫迭代器在 `__anext__` 抛 StopAsyncIteration / 异常时才释放，另提供 aclose
- **测试**：新增 tests/test_llm_limits.py 3 例（并发峰值 ≤ 上限、耗尽释放、异常释放）；相关 22 例全绿
- **面试话术**："成本控制第一层是并发天花板——进程内信号量限制同时在飞的 LLM 请求数，流式请求的额度要覆盖整个流生命周期并在异常时可靠归还。"

### C2 token 计量与每日成本预算（`f8833af`）
- **改动**：llm.py 进程级 usage 累计（`_usage_stats`，chat/流式/守卫流三路径都记录，流式走 `stream_options.include_usage`）；新增 app/core/budget.py（每用户每日 token 预算，超限 429，跨天自动清零）；chat 非流式/流式（finally 入账，含中断路径）与 ai-create 增量入账
- **原理**：token 是 LLM 成本的最小计量单位——没有计量就答不了"¥50/月怎么控"；预算按"用户×自然日"维度，先查后扣（超限在调用 LLM 之前拦截，不为超预算请求花一分钱）
- **踩坑**：① ai-create 原来 `finally: await llm.close()` 会关掉进程级单例客户端（W2-3 单例化后的隐患），顺手修复；② 流式 usage 只在最后一个 chunk 出现，守卫迭代器里统一捕获；③ DTZ005 要求 datetime.now 带时区
- **测试**：新增 tests/test_budget.py 3 例（预算累计/429/对话增量入账），全量 111 绿
- **面试话术**："成本预算=计量+限额：usage 全路径累计（含流式），按用户×自然日设 token 上限，超限在调模型之前就 429。"

### C3 查询嵌入缓存（`dc16819`）
- **改动**：EmbeddingService.embed 单条文本走 `_embed_one` 的 lru_cache（EMBED_QUERY_CACHE_SIZE=512），批量摄取不缓存
- **原理**：对话查询向量重复率极高（用户反复问相似问题/记忆去重反复嵌入相同事实），本地 ONNX 推理虽免费但占 CPU——缓存把重复推理变成内存查表
- **踩坑**：① 方法级 lru_cache 触发 ruff B019（内存泄漏）——服务是进程级单例，缓存随生命周期有效，noqa 注明理由；② fake 模型返回 list 没有 .tolist()，`_embed_one` 改为 `float(x) for x in vec` 兼容 numpy/纯列表
- **面试话术**："缓存按'高重复率'选点：查询向量、重排结果值得缓存，批量摄取不缓存（一次性的）——盲目全量缓存反而浪费内存。"

### C4 Rerank 结果缓存（`54101cf`）
- **改动**：Reranker._rerank_cached 按 (query, 候选集 tuple, top_n) 做 lru_cache（RERANK_CACHE_SIZE=128），线程池内执行
- **原理**：交叉编码器是检索链最重的推理环节（1GB 模型），多路召回的候选集在相近查询间重复率不低；缓存键基于内容（tuple）而非对象，命中即跳过全部推理
- **踩坑**：测试期望"单候选短路"被写成"不同候选集不命中"——单候选本来就不加载模型（calls 不变），改用两个段落的候选集断言
- **面试话术**："缓存键设计：按内容哈希（query+候选集），不按对象/指针——同一查询换一个请求对象也要命中。"

### C5 API 限流（`2463fcf`）
- **改动**：新增 app/core/rate_limit.py 通用滑动窗口限流器（deque 时间戳，allow 前先清过期）；chat（30 次/60s）与 ai-create（10 次/60s）按用户维度接入，超频 429
- **原理**：限流保护的是"昂贵接口"——对话与 AI 解析每次都烧 LLM 钱，必须按用户限频；滑动窗口比固定窗口平滑（不会出现窗口边界双倍放行）；登录限流是另一个独立场景（防爆破），保持 auth.py 原实现
- **踩坑**：无。依赖注入 `_quota: None = Depends(...)` 复用已解析的 get_current_user（FastAPI 依赖缓存），不会重复查库
- **面试话术**："限流分场景：登录限流防爆破，接口限流防刷钱——滑动窗口比固定窗口平滑，单实例内存实现、多实例换 Redis 的接口已经留好。"
