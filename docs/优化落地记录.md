## 二、逐项明细

### 1. `fix/cli-login` — CLI 登录鉴权（修复双入口破功）

- **问题**：`cli/copilot_cli/main.py` 的 `_request()` 不带 `Authorization`，而 `/chat`、`/todos` 全部走 `get_current_user` → CLI 所有命令返回 401，"CLI + Web 双入口"实际只有 Web 可用。
- **功能变化**：
  - 新增 `copilot login` / `copilot logout` / `copilot whoami` 命令。
  - 令牌持久化到 `~/.copilot/credentials.json`，支持 `COPILOT_TOKEN`（令牌）与 `COPILOT_CREDENTIALS`（文件路径）环境变量覆盖。
  - `_request` 自动注入 `Bearer`；401 时给出"请先运行 copilot login"的可执行指引。
  - `login` 支持 `--register` 直接注册新账号。
- **文件**：`cli/copilot_cli/auth.py`（新）、`cli/copilot_cli/main.py`、`cli/pyproject.toml`、`cli/tests/test_cli.py`（新）。
- **测试**：CLI 12 用例（凭据读写/环境变量优先级/鉴权注入/401 指引/命令流程）。

### 2. `feat/request-id-tracing` — 全链路追踪（对齐 §15）

- **问题**：无中间件、无 contextvars；WARN/ERROR 日志不带 request_id / user_id。
- **功能变化**：
  - 新增 `app/core/context.py`：`request_id`/`user_id` ContextVar + **纯 ASGI 中间件**（规避 `BaseHTTPMiddleware` 把下游放进独立任务导致 contextvar 不传播的坑）。
  - 响应头回写 `X-Request-ID`，支持客户端透传。
  - 日志格式变为 `... | [request_id] | ...`，`user_id` 由 `get_current_user` 写入。
- **文件**：`backend/app/core/context.py`（新）、`core/logging.py`、`main.py`、`api/deps.py`、`tests/test_context.py`（新）。
- **测试**：+4 用例（生成/透传/过滤器/默认值）。

### 3. `perf/docs-list-n-plus-one` — 文档列表 N+1

- **问题**：`_to_out` 对列表中每个文档各执行一次 `SELECT count(*)`。
- **功能变化**：新增 `_chunk_counts()`，用一条 `GROUP BY document_id` 聚合回填 `chunk_count`。
- **文件**：`backend/app/api/routes/documents.py`、`tests/test_documents_list.py`（新）。
- **测试**：查询数回归断言（分块 count 从 N 条降为 1 条）。

### 4. `feat/structured-output` — 结构化输出容错

- **问题**：Supervisor 用正则抓 JSON、记忆提取裸 `json.loads`（失败**静默丢数据**）、待办解析无容错。
- **功能变化**：

  - `LLMClient.chat` 支持 `response_format={"type":"json_object"}`。
  - 查询改写 / 记忆提取 / 待办 AI 解析接入；Supervisor 路由 JSON 优先、正则兜底。
- **文件**：`core/json_parse.py`（新）、`core/llm.py`、`agent/langgraph_engine.py`、`memory/service.py`、`rag/query_rewriter.py`、`api/routes/todos.py`、`tests/test_json_parse.py`（新）+ 7 个测试 Fake 签名同步。

### 9. `feat/doc-dedup-retry` — 文档去重 + 失败重试

  - 前端 `KbPanel` 对 `failed` 文档显示"重试摄取"按钮。
- **数据库**：新增列 + 索引，Alembic 迁移 `d5a1c7e9f2b3`（可回滚）。
- **文件**：`backend/app/models/document.py`、`alembic/versions/d5a1c7e9f2b3_add_documents_content_hash.py`（新）、`backend/app/api/routes/documents.py`、`tests/test_doc_dedup_retry.py`（新）、`web/src/api.ts`、`web/src/components/KbPanel.tsx`。
- **测试**：+3 用例（去重/重试成功/越权 404）。

### 10. `refactor/prompt-centralization` — Prompt 集中管理（§18）

- **问题**：6 个模块硬编码 prompt，无集中目录、无版本。
- **功能变化**：新增 `app/core/prompts/`（agent/chat/memory/rag/todo 分文件 + `PROMPT_VERSION="1.0.0"`）；6 处改为引用；安全边界段与模板变量保持。

### 11. `feat/context-token-budget` — 滚动历史 token 预算

- **问题**：上下文只按"条数"窗口裁剪，长消息（工具结果/长文）在条数内仍会撑爆上下文与成本。
- **功能变化**：

  - 新增配置 `HISTORY_MAX_TOKENS`（默认 4000，0=不限）。
- **配置三件套**：`core/config.py` + `backend/.env.example` + `deploy/.env.example` 已同步。
- **文件**：`backend/app/agent/base.py`、`core/config.py`、`backend/.env.example`、`deploy/.env.example`、`tests/test_context_budget.py`（新）。
- **测试**：+4 用例。

**关键实现细节 / 踩坑**
- **统一响应不能用 `route_class`**：FastAPI 0.141 的 `include_router` 使用惰性 `_IncludedRouter`，且子路由 `route_class` 在 app 层重建时丢失。最终改用**纯 ASGI 中间件**，仅在 `/api/v1` 且 2xx 且 `application/json` 时缓冲包壳；SSE / 导出 Markdown / `/openapi.json` / 根路径天然不被包装。
- **分页响应契约**：列表 `data` 由数组变为 `{items,total,page,page_size}`；前端 `fetchSessions/fetchTodos/fetchDocs` 统一解包 `items`，组件零改动。
- **HITL 复用 `Message.extra`**：无需新表/迁移。流式场景新增 `event: pending`，前端据此展示确认条，避免"流式结束后再拉消息"覆盖已渲染内容。
- **`registry.register` 兼容两写法**：`@registry.register` 与 `@registry.register(requires_confirmation=True)`。

### 补充修复：UTF-16 文本 NUL 导致同步 500

- **现象**：点击「同步」返回 500：`asyncpg CharacterNotInRepertoireError: 无效的 "UTF8" 字节序列: 0x00`（`INSERT INTO chunks ... content` 含 `\x00`）。

- **修复**：`parsers/base.py` 新增 `decode_text()`（BOM/UTF-16/GBK 探测 + **去 NUL**），Markdown/Code/Web/Wiki 解析统一使用；`pipeline` 入库前再兜底 `replace("\x00","")`。
- **验证**：真实 `requirements.txt`（5130 个 NUL）解码后 **0 NUL**；后端 **219 用例 / 80.16%**、ruff 全过。

### 🚨 事故修复：删除空间误删用户本地目录（严重）

- **现象**：点「删除空间」后，`D:\知识库\知识库`（local 空间指向的真实目录）**内容被整个删除**。
- **根因**：删除路由**无条件** `shutil.rmtree(space.root_path)`。local 空间的 `root_path` 是用户真实目录（绝对路径），被当受管副本删了。`shutil.rmtree` 不进回收站。

- **防回归**：新增测试「删除 local 空间后用户文件仍在」「upload 空间删除会清理受管副本」。
- **教训（写进 AGENTS §6）**：任何删除/清理操作，必须先判定"受管副本 vs 外部真实路径"，禁止对外部路径做 rmtree；破坏性操作要有测试兜底。

## 十四、批次 R2 · Q1 回答轨迹（可观测地基）

**原理**：多智能体没有轨迹就不可调试、不可评测（Q0.7）——子 Agent 越多，"为什么是这个回答"越无法归因；先补可观测地基（路由判定 / 节点序列 / 工具调用 / 各步耗时全量落库），再扩子 Agent。轨迹同时是 R5 双引擎对照评测的现成数据源。

**踩坑（本批实际踩到的）**
1. **GBK 控制台不可信**：控制台输出中文会乱码，核对文档/标签必须走 Python（`ascii()` / `difflib` 比对），不能"肉眼看终端"。
2. **`re.IGNORECASE` 与"直觉正则"冲突**：敏感 key 首版用 `(?![a-z0-9])` 作尾随保护，而 `re.IGNORECASE` 下 `[a-z]` 同样匹配 `A-Z`，于是 `secretKey` **没有被脱敏**（大写 `K`"匹配"了 `[a-z]`、负向前瞻失败）。改为大小写受限的前瞻 `(?-i:(?![a-z0-9]))` 才修好——既保住 `max_tokens` 的白名单豁免（小写 `s`），又能识别 camelCase 后缀。只因为有测试专门断言 `secretKey` 才被发现。
3. **手写引擎有 6 个出口点**：`run()` 三处 + `run_stream()` 三处（普通回复 / 待确认 / 达最大轮次）。漏掉任一处会**静默**产出不含 `answer` 步骤的轨迹。解法：所有出口统一走同一个 seal 收口函数。
4. **Ant Design `Collapse` 懒挂载**：组件测试必须先点击 header 才能断言步骤内容，写在点击之前的断言会以"看不懂的原因"失败。
5. **StrictMode 敏感的不可变更新曾有四份拷贝**：`ChatPanel.tsx` 的 `onChunk` / `onPending` / `onDone` / `onError` 各写一份，其中带"避免重复追加"注释的那份最易写歪；收归为唯一的 `updateLastAssistant` 助手。
6. **并行 pytest 抢同一个 `copilot_test` 库**（fixture `ERROR at setup`）：验收必须串行跑。
7. **边界克制**：轨迹接入**没有动 SSE 契约**——只是既有 `done` 事件 data 里多一个可选键，事件列表与"已落库"语义保持不变。

**测试结果（闸门提交 `d2815f6`）**：后端 **370 用例 / 覆盖率 82.81%**、`ruff check .` 全过；前端 **101 用例 / 19 个文件**、`npm run build`（`tsc -b`）零错误；CLI **15 用例**。批次起点基线为后端 343 用例 / 82.53%、前端 92 用例 / 18 文件。

**面试一句话话术**：多智能体不是黑盒——每次回答的路由判定、选中子 Agent、工具调用序列与各步耗时全量落库并可展开回放；轨迹与密钥做了硬隔离（正则脱敏 + 用例守护）。

**冻结候选（本批发现但未做）**
- **实时（渐进式）轨迹流**：目前只在"回答结束后可见"——轨迹搭 SSE `done` 事件顺带下发；实时化需要新增事件与前端增量合并逻辑，收益不抵本批复杂度 → 冻结。
- **`onPending`（HITL）无测试**：待确认回调缺一个"真正调用它"的用例，HITL 分支回归无守护 → 冻结（本批未改该路径）。
- **`onError` 的 push（else）分支无测试**：既有出错用例走到的是「最后一条是空助手消息」的更新分支；`web/src/components/ChatPanel.tsx` 中「末尾不是助手消息 → 追加新消息」那条兜底分支没有任何用例到达 → 冻结。
- **`ChatPanel.tsx` 第三套"最后一条助手消息"选取规则**：HITL 告警条另用一套判据（与 `updateLastAssistant` 不一致），存在分叉风险 → 冻结，未在文档任务中顺手改。
- **复数/小写复合密钥 key 不在脱敏范围**：`apiKeys` / `credentials` / `tokens` / `secrets` 这类复数或小写复合 key 名不会命中敏感词正则——尾随保护 `(?-i:(?![a-z0-9]))` 要求敏感词后不接小写字母/数字，而这条规则正是让 `max_tokens`、`tokens_total` 免于误伤的同一道闸；代价是 `credentials`（以 `s` 结尾）这类现实的密钥容器名被一并放过。因当前无任何工具传入此类 key，暂不扩规则 → 冻结。

- **① 心跳截断（`743cdae` + `41d0880`）**：`app/api/routes/chat.py` 的流循环原用 `asyncio.wait_for(anext(gen), timeout=_HEARTBEAT_SECONDS)` 取下一分片；改为把 `anext` 挂成持久 Task（`asyncio.ensure_future`）后用 `asyncio.wait` 跨超时复用，超时只发 `: ping` 保活而不动生成器。`finally` 中显式 `cancel()` 并 await 悬挂的 `pending_chunk`（客户端断开时不再留下持有引擎的任务），同时消除 `pending` 名字复用。
- **② 独白泄漏（`6c74471` + `0e52eca`）**：LangGraph 引擎按「模型轮」缓冲 `on_chat_model_stream` 的文本，在 `on_chat_model_end` 依据该轮 `tool_calls` 是否为空决定「产出」或「丢弃」；`output` 缺失时 fail-closed 按工具轮处理并 WARNING。手写 `Orchestrator` 同口径。工具轮耗尽 `max_turns` 且全程无文本产出时，用叶子节点收尾文本兜底（不再给空回复）。
- **③ 新会话自杀（`19c12a8`）**：`web/src/components/ChatPanel.tsx` 的 `onSessionCreated={setSessionId}` 使 `sessionId` 从 `null` 变新 id，触发依赖 `[initialMessages, sessionId]` 的 effect，abort 掉刚发起的请求 → 首条消息永远发不出去。
- 新增测试：`backend/tests/test_chat_stream_heartbeat.py`（166 行）、`backend/tests/test_stream_no_narration.py`（224 行）；前端 `ChatPanel.test.tsx` 补首条消息用例。

**原理**：三个缺陷同属「流式链路的完成语义被破坏」，但根因各异——① 是超时取消语义（`wait_for` 会取消 `anext`，把异步生成器就地终止）；② 是「content 与 tool_calls 互斥」这个写死在注释里的模型假设被真实模型打破；③ 是 React effect 依赖错误导致请求自杀。修法的共同原则：**「完成」必须由真正的收尾代码判定，任何中间态（心跳超时、缺失的 payload、会话创建）都不得冒充成功**；同时保持可用性（兜底文本、fail-closed 宁丢独白不泄露）。

**踩坑（本批实际踩到的）**
1. **`asyncio.wait_for(anext(gen), timeout=…)` 超时会取消 `anext`**，把异步生成器就地终止；流循环随后把 `StopAsyncIteration` 当「正常结束」→ 落库 + 发 `done`。表现是「回答被静默截断却显示成功」，且 `citations`/`trajectory` 一起丢（它们只在 `run_stream` 收尾代码里拷贝）。
2. **「工具调用轮 content 为空、纯文本轮 tool_calls 为空，二者互斥」是写死在两个引擎注释里的假设，被真实模型打破**（实测落库正文 = `"I'll check your todo list for you.你的待办列表如下：…"`）。因此不能靠「content 非空」判定回答轮，必须读结构化 `tool_calls`。
3. **定位上的不对称现象：同一进程内非流式正常、流式异常**——因为只有流式路径依赖心跳循环；非流式直接 `await` 完整结果，绕过了 `wait_for`。这提示问题在传输/保活层，而非模型或工具层。
4. **复现时踩到的坑：Qdrant 本地模式有文件锁**，服务在跑时无法在进程内复现（本地嵌入/向量库被占用），必须打运行中的服务做黑盒复现。
5. **首条消息自杀的机制**：`onSessionCreated={setSessionId}` 让 `sessionId` 从 `null` 变新 id，触发了那个依赖 `[initialMessages, sessionId]` 的 effect，把刚发起的请求 abort 掉。
6. **诊断过程中我自己的两次测量失误（如实记）**：
   - asyncpg 把 json 列返回成字符串，导致用 `in` 做的是子串测试而非包含判断，一度误判「两个引擎都没有轨迹」；
   - 抓 SSE 时抓的是「最后一条非空 `data`」而不是「`done` 事件的 `data`」，把 `chunk` 的 data 当成了 `done` 的 data，误读事件序列。

**测试结果（tip `19c12a8`）**：后端 **379 用例 / 覆盖率 83.40%**、`ruff check .` 全过；前端 **104 用例 / 19 个文件**、`npm run build`（`tsc -b`）零错误。R2 起点：后端 370 / 82.81%、前端 101 / 19 文件。
**验收（真实模型端到端，LangGraph 引擎，打运行中的服务）**
- **Q1 `帮我看一下我的待办列表`**（路由 tools → `todo_list`）：事件序列 `session,chunk,done`，无 `error`；流式文本为完整中文待办概览，无英文独白；落库 `extra` = `{tool_calls, trajectory}`；流式拼接 == 落库 `content`（546 == 546）。
- **Q2 `帮我看看wiki里有什么`**（路由 kb → `kb_search`）：事件序列 `session,chunk,done`，无 `error`；启动后 **19.4s 静默**（请求→首片 19.63s、会话事件→首片 19.44s，期间发 **1** 次心跳），回答仍完整返回；无英文独白；落库 `extra` = `{citations, tool_calls, trajectory}`；流式拼接 == 落库 `content`（861 == 861）。
- 说明：绑定工具的节点按「模型轮」缓冲，故整段回答为单个 `chunk`，没有「相邻 chunk 间隔」可测；上表静默量取「会话事件→首个 chunk」的真实等待，**未人为制造**。

**面试一句话话术**：SSE 流式不是「把 token 转发出去」就完了——心跳保活必须与生成器取消语义解耦（`wait_for` 会杀死 `anext`），「一轮文本是不是回答」必须看结构化 `tool_calls` 而不是猜 content 是否为空，否则真实模型会同时给你「静默截断却报成功」和「英文独白混进答案」；修完这两点再补 React effect 依赖错误（新会话首条消息自杀），才算把流式链路的完成语义做对。

**冻结候选（本批发现但未做）**
- **「逐字流式 + 无独白」不可兼得**：绑定工具的节点无法预判当前轮是否已是回答轮，只能整轮缓冲后一次性产出（实测表现为单个 `chunk`）。若要两者兼得，需新增一个 additive 的「替换正文」SSE 事件（先流式、判定为独白后再撤回/替换），属独立改动 → 冻结。
- **`_STREAM_MAX_SECONDS` 仍是模块常量**（非配置项三件套）：运维如需可调，再提升为配置项（补 `config.py` + 两份 `.env.example` + 启动校验）→ 冻结。
- **手写引擎整体不再逐字流式**：每轮都可能调工具、无法预判轮次，只能整轮缓冲；与 LangGraph 绑定工具节点同口径 → 冻结。
- **`GenericFakeChatModel` 流式下丢 `tool_calls`**：导致测试必须 override `_stream` 才能覆盖 fail-closed 分支——测试夹具与真实模型的保真度差异需长期留意 → 冻结。
