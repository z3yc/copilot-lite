# 知识库 Wiki 接入 —— 技术选型与路线复盘

> 用途：面试复盘 / 技术决策留痕。重点回答"**为什么这么选、为什么不选另一种**"。
> 关联方案：`docs/知识库Wiki技术方案.md`（v2 收敛版）。
> 记录时间：2026-09-11。

---

## 0. 需求一句话

把本地 **Obsidian Wiki（Markdown 双链笔记）** 接入现有 RAG 知识库：**手动导入 + 只读 + 手动/定时同步 + 双链图谱可视化 + 检索增强**，并**兼容后续云端部署**。

---

## 1. 路线级选型（大方向）

### 1.1 Wiki 来源：本地 Markdown vault / 应用内自建 / 外部 Wiki 服务

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 本地 Markdown vault（Obsidian/Logseq）** | 复用现有 md 解析与摄取 pipeline；双链可静态解析；零外部依赖；贴合"本地知识库"；用户已有资产直接可用 | 需文件系统访问；要处理增量/删除 | ✅ **选 A** |
| B. 应用内自建 Wiki（DB 存页面） | 端到端可控、天然多用户 | 要自造编辑/存储/渲染/版本，偏离"RAG 主线"，工量大 | ❌ 不做（远期可选） |
| C. 对接外部 Wiki 服务（MediaWiki/Outline） | 功能全 | 引入容器/账号/网络/鉴权，个人项目成本过高 | ❌ 不选 |

**为什么是 A**：项目的核心命题是"RAG + Agent"，Wiki 只是**知识来源**。选 A 只需新增一个解析器 + 一层同步，**复用已有的 `ingest_document` / `hybrid_search` / Qdrant / 用户隔离**，投入产出比最高。

### 1.2 部署形态决定的关键设计：直读用户目录 vs 受管副本

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 直接扫描用户本机/服务器目录 | 实现最简单 | **云端后端访问不到用户本机目录**；目录被改坏有风险 | ❌ |
| **后端"受管副本" + 导入通道** | 本地（路径导入）与云端（zip 上传）**同一套同步逻辑**；副本可挂卷、可审计、只读扫描 | 多一步导入/落盘 | ✅ **选受管副本** |

**为什么**：需求明确"要考虑后续云端"。若同步逻辑绑定"本机路径"，上云即报废。**把 vault 先导入为后端受管副本（`backend/data/wiki/{scope}/{space}/`），同步永远针对副本**——本地用路径导入、云端用 zip 上传，两种形态共用一套代码。这是"部署形态倒逼架构"的典型取舍。

### 1.3 读写：只读 vs 可编辑写回

- **选只读**。写回文件涉及：并发写、冲突解决、版本/回滚、路径沙箱放宽、审计。收益（在 Web 里编辑笔记）对个人场景有限。
- 面试讲法："**先把'读'的链路做深（解析/链接/检索增强），'写'是产品体验问题，不是知识库能力问题**，优先级明确靠后。"

### 1.4 同步：手动 / 定时 / 文件监听（watchdog）

- **选"手动 + 定时"**。文件监听（watchdog）在容器/云端、多副本、网络盘下不可靠（事件丢失、inotify 限制），且要处理防抖与并发。
- 定时扫描 + 手动触发是**幂等且形态无关**的方案，云端同样可用。
- 面试讲法："监听是'即时性'优化，扫描是'正确性'基础；**先保证正确与幂等，再谈实时**。"

## 2. 图谱可视化选型

需求：知识图谱可视化（力导向）。

| 方案 | 是什么 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **d3-force** | 力导向**布局算法库**（只算坐标） | 体积极小、完全可控 | **渲染/交互全自己写**（等价于自研图组件） | ❌ 与"用现成库"诉求相悖 |
| **react-force-graph-2d** | 封装 d3-force 的 **React 组件**（Canvas 2D） | **开箱即用**：拖拽/缩放/hover/点击/自定义节点；不引 three.js | 定制上限不如纯 d3 | ✅ **选它** |
| react-force-graph（全家桶） | 含 2D/3D/VR/AR | 要 3D 时开箱 | **3D 打包 three.js，体积巨大** | 需要 3D 再换 |
| @antv/g6 | AntV 图分析库 | 多布局/边类型，贴 antd 生态 | 学习成本、力导向场景偏重 | 备选 |
| 自研 Canvas/SVG | 完全自己写 | 无依赖 | 重复造轮子 | ❌ |

**为什么不选 d3-force**：它只提供物理模拟，节点/边绘制、缩放拖拽、tooltip、点击都要自写——**用户明确"用现成、不自研"**。
**为什么是 `-2d` 单包**：项目前端 antd chunk 已 900KB+，`react-force-graph` 全家桶会拖入 three.js；2D 单包体积可控，后续要 3D 直接换包、API 一致。
**面试讲法**："选型先看**团队/项目的真实约束**——这里约束是'快速出效果 + 控制包体'，所以选组件级现成方案；d3-force 是更底层的原语，灵活但等于自研。"

## 3. 本体（Ontology）：要不要？—— 本项目**不做完整本体**

### 3.1 概念区分（最容易讲混的点）
| 维度 | Wiki 双链（文档图） | 知识图谱（KG） | 本体（Ontology） |
|---|---|---|---|
| 层次 | **实例** | **实例（结构化）** | **模式 / schema** |
| 节点·边 | 页面·无类型链接 | 实体·**类型化关系**（`青木—准备→后端面试`） | 定义"有哪些概念/关系/约束" |
| 产生 | 人工写 `[[ ]]` | LLM/规则抽取 | 领域专家设计 |
| 形式化 | 非形式 | 半形式（可图查询） | 形式（RDFS/OWL，可推理） |
| 推理 | 无 | 有限（多跳遍历） | 强（分类/传递/逆/基数约束） |
| 维护成本 | 低 | 中 | **高** |
| 存储 | 普通表 | 图库/三元组表 | 本体文件 + 推理机 |

> 一句话：**双链是"实例级文档图"，KG 是"实例级实体关系图"，本体是"定义前两者如何组织的模式/词典"**。不是替代关系，而是"实例 ↔ 模式"。

### 3.2 为什么不做完整本体（OWL + 推理机 + SPARQL）
- 收益集中在对**强约束/强推理**有刚需的领域（医疗、法律、供应链、企业主数据）；个人助理知识库到不了这个收益拐点。
- 成本：本体设计、抽取映射、推理引擎、存储（图库）、评估与维护，全部是持续性投入。
- 违背项目原则"**不为未来过度设计**"。

### 3.3 折中路线：M4 可选「轻量本体（类型化链接）」
- 定义约 8 个**受控关系**（`instance_of / part_of / depends_on / derived_from / related_to / authored_by / references / contradicts`）+ 少量实体类型（`Concept/Project/Person/Tool/Note`）。
- 用 LLM 给**已有双链**批量打关系标签 → 存 `wiki_link.relation`；失败降级为无类型边。
- 收益：图谱边有语义（着色/过滤）、多跳检索可按关系加权、"某概念属于哪个项目"这类结构化问法；成本远低于完整本体。
- 面试讲法："**我知道本体的价值与边界，但在个人知识库场景它是过度设计；我用'受控词表 + 类型化链接'拿到 80% 收益、10% 成本。**"

## 4. 同步与数据模型的关键取舍

| 决策 | 选择 | 为什么 / 不选另一种 |
|---|---|---|
| 幂等主键 | **`wiki_space + rel_path`** | 用 content_hash 当主键：改一个字就变"新文档"，产生重复向量。rel_path 才对应"同一页"。 |
| 重命名检测 | **内容 hash 相同 + rel_path 变 → 视为"移动"** | 避免重命名导致重复摄取/重嵌入（省成本、保链接）。 |
| 更新策略 | **删旧 chunks+向量 → 重摄取**（先算后写） | 跨"关系库+向量库"无单库事务，沿用 pipeline 既有"失败补偿"思路。 |
| 删除 | **级联清理 page/chunks/向量/link** | 防止孤儿数据污染检索。 |
| 索引类型 | `documents.source_type="wiki"` | 复用现有文档/分块/检索/引用链路，不另起一套。 |

## 5. 检索增强：链接图驱动召回

- **做法**：混合检索 TopN → 取命中页的 **1-hop 出链/入链页** → 各取 Top1 块 → 合并去重 → **Rerank** → 注入。
- **为什么**：RAG 的经典缺口是"**答案在关联页，但不与问题字面相似**"。双链图提供了"语义之外的关联信号"，是 Wiki 相比普通文档库的**独有增量**。
- **为什么不无限扩展**：1-hop 已覆盖大部分收益；多跳会引入噪声与成本。用 `WIKI_LINK_EXPANSION_ENABLED` / `WIKI_EXPAND_HOPS` 开关，便于 A/B。
- **面试讲法**："检索增强要**可开关、可度量**——我会用现有 RAG 评测（recall@K/MRR）对比开关前后，而不是拍脑袋加。"

## 6. 安全取舍（§6 红线）

| 面 | 措施 | 为什么 |
|---|---|---|
| 路径穿越 | `Path(root).resolve()` 后必须 `is_relative_to(受管根)`；拒绝 `..`/绝对路径/软链 | 文件名/路径来自用户，拼接即漏洞（本项目上传接口已有同类教训） |
| zip 炸弹 | 限压缩包大小、条目数、解压后总大小；拒绝穿越条目 | 解压是典型 DoS/任意写入口 |
| 用户隔离 | `space.owner_id` 绑定；`kb_search` 复用既有 `user_id` 过滤 | 隔离必须穿透到**检索/召回链路**，不只是 REST |
| Prompt 注入 | Wiki 正文进 prompt 走既有定界 + "仅数据非指令"声明 | Wiki 内容与检索结果同为不可信外部数据 |
| XSS | Wiki 正文渲染复用 `DOMPurify` 唯一入口 | 存储型 XSS 高危，且 Wiki 内容作者可控 |

## 7. 路线总览（里程碑 + 面试一句话）

| 里程碑 | 内容 | 一句话话术 |
|---|---|---|
| M1 导入与索引 | 受管副本 + 本地/zip 导入 + WikiParser + 增量同步 | "先打通'导入→索引→可检索'，并保证幂等与云端兼容" |
| M2 双链与检索增强 | 链接图 + 反向链接 + 邻居扩展召回 | "用链接图补 RAG 的'关联召回'缺口，可开关可评测" |
| M3 图谱可视化 | `/wiki/graph` + `react-force-graph-2d` | "现成组件快速出效果，控制包体，3D 可平滑升级" |
| M4 轻量本体（可选） | 类型化链接 + 按关系加权/着色 | "不盲目上完整本体，用受控词表拿 80% 收益" |

**贯穿原则**：复用现有 RAG 链路、幂等可回退、安全穿透到检索层、选型服从项目真实约束（部署形态/包体/工期）。

## 8. 高频追问速答

- **"为什么不用 Neo4j 存链接图？"** → 链接图规模小（个人 vault 千级页面），PostgreSQL 两张表 + 索引足够；引入图库是为"大规模多跳查询/图算法"，当前用不上，属过度设计。
- **"双链和知识图谱什么关系？"** → 双链是实例级文档图；KG 是实例级实体关系图，边有类型；本体是定义 KG 的 schema。
- **"为什么只读？"** → 写回要处理并发/冲突/版本/审计，收益低；先把读链路做深。
- **"云端怎么拿本地 vault？"** → 导入通道：本地走路径、云端走 zip 上传；同步永远针对后端受管副本，形态无关。
- **"如何保证同步不重复？"** → 以 `rel_path` 幂等 + 内容 hash 识别移动 + 只重嵌变更页。
