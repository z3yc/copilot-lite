## 一、项目介绍（30 秒电梯陈述）

**一句话版**：
> 我独立开发了一个**个人 AI 智能助理** Copilot-Lite：基于 DeepSeek 大模型 + 自研 Agent 编排 + 企业级 RAG 知识库，支持多轮对话、工具调用（待办/知识库检索）、CLI 和 Web 双入口，本地一键启动，Docker Compose 云端部署。

**扩展版（30 秒）**：
> 项目核心有三层：① **Agent 层**——手写 ReAct 循环 + Function Calling，通过可插拔工具注册表扩展能力；② **RAG 层**——多格式文档解析、智能分块、BGE 本地嵌入、Qdrant 向量库 + BM25 混合检索 + RRF 融合，回答带引用溯源；③ **工程层**——FastAPI 异步后端、SSE 流式前端、31 个测试覆盖率 83%、CI 流水线、Docker 一键部署。核心逻辑全部手写，不依赖 LangChain，以深入理解大模型应用工程。

## 二、架构与选型

**Q1：为什么选 FastAPI？**
> 一句话：异步性能 + 类型安全 + 自动文档。
> 深入：FastAPI 基于 ASGI 标准（Starlette），原生支持 async/await，适合 LLM 场景的高并发 IO（调用 DeepSeek API、流式输出）；Pydantic 自动校验请求/响应并生成 OpenAPI 文档（/docs 可直接调试）；依赖注入系统天然适合封装数据库会话等资源。

**Q2：为什么不用 LangChain？**
> 一句话：手写才能讲清楚原理，调包会被质疑"只会拼积木"。
> 深入：LangChain 抽象重、版本迭代激进、调试黑盒。我的场景（单用户、5 个工具、1 个模型）手写完全可控。但**设计模式借鉴了它**：ToolRegistry 对应 BaseTool、Orchestrator 对应 AgentExecutor、HISTORY_WINDOW 对应 Memory 裁剪。面试可对比两种方案的取舍。

**Q3：项目的分层架构？**
> 五层：客户端层（CLI/Web）→ API 层（FastAPI REST+SSE）→ Agent 核心层（编排/记忆/工具）→ 知识库层（解析/分块/检索）→ 存储层（PostgreSQL/Qdrant）。关键设计：**前端只是壳，CLI 与 Web 共用同一套后端 API**；Agent 与 RAG 通过工具注册表解耦。

**Q4：为什么预留多智能体扩展？**
> 通过 BaseAgent 抽象协议 + Agent-as-Tool 模式预留：未来 RouterAgent 意图路由分发到子 Agent，子 Agent 可注册为工具复用现有协议。设计原则：**不为未来过度设计，但为未来留好接口**。

## 三、Agent 核心

**Q5：ReAct 循环的原理？**
> ReAct = Reason + Act。循环内：模型"思考"（生成文本或工具调用）→ 若请求工具则"行动"（执行工具）→ 结果回填消息 → 再次让模型推理，直到模型输出最终回答。我的实现有**最大轮数保护**（AGENT_MAX_TURNS=5），防止死循环。

**Q6：Function Calling 是什么？和 ReAct 什么关系？**
> Function Calling 是模型 API 的能力：把工具定义（JSON Schema）传给模型，模型"选择"调用哪个工具并返回结构化参数。ReAct 是循环框架，Function Calling 是其中"决策"环节的协议。我的编排器用 Function Calling 驱动 ReAct 循环。

**Q7：工具注册表怎么设计？新增一个工具要几步？**
> 三步：写 async 函数（第一个参数是注入的 ToolContext，其余参数自动生成 JSON Schema）→ 加 @registry.register 装饰器 → 完成。装饰器从函数签名自动推断参数类型和必填项，docstring 第一行作为工具描述。执行时统一做 JSON 参数解析、异常兜底（错误转字符串返回，不中断循环）。

**Q8：ToolContext 是什么？为什么需要？**
> 工具执行上下文：注入数据库会话、当前用户等。工具函数通过 ctx 无感使用数据库，不需要自己管理连接。同时保证了工具的"无状态"——依赖显式注入而非全局变量。

**Q9：记忆系统怎么实现的？**
> 双层：① 短期记忆——历史消息窗口（最近 20 条）随对话传给模型；② 长期记忆（预留）——事实提取→向量化→按相关性召回注入。当前 P1 实现了窗口裁剪，长期记忆在路线图中（ER 图已有 MEMORY_FACT 表设计）。

**Q10：如何防止 Agent 乱调工具？**
> 四层防护：系统提示约束（何时该调工具）；工具参数 JSON Schema 校验（TypeError 兜底）；最大轮数保护；工具白名单注册制（只有注册过的才能被调用）。

## 四、RAG 知识库

**Q11：RAG 为什么优于"微调模型"？**
> 知识可实时更新（不用重新训练）、答案可溯源、成本低（微调大模型成本极高且知识会过期）。RAG 适合"私有知识问答"场景，微调适合"改变模型行为风格"。

**Q12：混合检索为什么优于纯向量检索？**
> 向量检索擅长语义泛化（"框架特点"命中"性能高"），但对专有名词/代码符号/ID 不敏感；BM25 字面命中精准但无语义。两者 RRF 融合互补。面试追问"为什么不用加权求和"→ 两路分数量纲不同（余弦 vs 词频），RRF 只看排名，无参稳定。

**Q13：RRF 融合的原理？**
> score = Σ 1/(k+rank)，k=60。两路检索各自按排名打分，同一文档在两路中排名都靠前则融合分高。只看排名不看分数绝对值，避免量纲问题，无需调权重。

**Q14：分块策略？**
> 三层：① 标题路径栈锚定（块携带完整标题链，如 ["第一章","第一节"]）；② 段落聚合（短章节整体成块，长章节按段落聚合到 800 字符）；③ 重叠控制（相邻块保留 100 字符重叠，防语义切断）。面试追问"分块大小怎么定"→ 权衡检索精度与上下文碎片化，可配置，进阶用语义边界分块。

**Q15：嵌入模型为什么选 BGE 本地？**
> DeepSeek 无 embedding API；BGE-small-zh-v1.5 中文效果好、512 维、本地免费离线；fastembed 用 ONNX 运行时（~50MB），远轻于 torch 方案。国内网络走 hf-mirror 镜像。

**Q16：为什么不用 Docker 也能跑 Qdrant？**
> qdrant-client 支持嵌入式本地模式 `QdrantClient(path=...)`，数据落磁盘零服务器。配置里 QDRANT_URL 指向远程时自动切换 http 模式（云端部署用 Docker 版 Qdrant）。同一份代码本地/云端无缝切换。

**Q17：引用溯源怎么实现的？**
> 源头在分块：每块带元数据（标题路径/页码）→ 检索时元数据随 payload 返回 → kb_search 工具把"来源"格式化为"文档标题 > 章节 > 页码" → 系统提示要求模型回答时注明来源。

**Q18：如何降低幻觉？**
> 三层：系统提示约束"只基于检索内容回答"；检索不到时工具返回空，模型如实说"未找到"；回答带引用可追溯，用户可验证。

## 五、工程与部署

**Q19：SSE 流式怎么实现的？**
> 后端 POST /chat/stream 返回 text/event-stream，事件序列 session→chunk→done；前端 fetch + ReadableStream 逐块解析渲染打字机效果。LLMClient.stream_chat 已封装模型侧 token 级流式（可无缝升级）。Nginx 反代时需 proxy_buffering off（部署文档已配置）。

**Q20：数据库为什么 SQLite/PostgreSQL 双支持？**
> 开发零依赖（SQLite 克隆即跑），生产同构（PostgreSQL 已配置）。表结构统一由 Alembic 迁移管理，两种库共用同一套迁移文件。这是"开发体验"与"生产一致性"的平衡。

**Q21：测试策略？覆盖率 83% 怎么保证的？**
> 三层：单元测试（解析器/分块/工具注册表）、集成测试（chat API/会话/Todo/SSE）、流水线测试（摄取）。技巧：**FakeLLM 模拟模型响应、伪嵌入（哈希向量）避免下载模型**，测试秒级跑完。覆盖率 fail-under=80 强制，CI 不达标直接失败。

**Q22：CI 流水线做什么？**
> 后端：ruff + pytest（含覆盖率门槛）；前端：tsc 类型检查 + vite 构建。GitHub Actions 标准格式（Gitee 可对接 Gitee Go）。

**Q23：云端部署方案？成本？**
> 2C4G 轻量服务器（¥30-50/月），Docker Compose 编排：postgres+qdrant+redis+backend+web（Nginx）。DeepSeek 按量付费个人量级每月几元。总成本 <¥60/月。详见 `deploy/DEPLOY.md`。

**Q24：生产环境的隐患与对策？**
> ① API Key 泄露 → .env 全 gitignore + 部署用 env_file；② 模型下载失败 → hf-mirror + 禁用 xet；③ SSE 被缓冲 → Nginx 关 proxy_buffering；④ 大文档摄取阻塞 → 当前同步（个人量级够用），大数据量改后台任务；⑤ 敏感数据 → 云端只放脱敏示例（混合模式）。

## 六、项目亮点总结（结尾话术）

> 这个项目让我完整走了一遍**大模型应用工程的闭环**：从模型接入、Agent 编排、RAG 检索、前端流式到 CI/CD 与云端部署。最大的收获不是某个框架，而是**理解每个环节为什么这么设计**——比如混合检索解决什么问题、覆盖率为什么能抓出真实 bug（工具字符串二次序列化）、配置与启动目录解耦的坑。技术上敢手写核心逻辑，工程上有测试和 CI 兜底，这是我作为后端候选人的证明。
