## 1. 现状盘点（先摆事实，再谈选择）

| 事实 | 代码证据 |
|---|---|
| **已经有两种引擎，可切换** | `AGENT_ENGINE`：手写 `Orchestrator`（单 Agent ReAct）↔ `LangGraphEngine`（supervisor 多智能体） |
| **两引擎共用一套工具注册表** | `langgraph_engine.py:39,152` 用 `global_registry`；执行统一走 `registry.execute` |
| **“多智能体”实质 = 工具子集收窄** | `AGENT_TOOLS = {"kb_agent": ["kb_search"], "tools_agent": None, "chat_agent": []}` |
| **当前多智能体没有回环/协作** | 图结构：`START → supervisor → {kb,tools,chat}_agent → END`，子 agent 之间不通信 |
| **路由有兜底，说明路由本身脆弱** | `_keyword_route()`：LLM 判不准时的关键词兜底 |
| **接口层已平权** | 两引擎都实现 `last_tool_calls` / `pending_confirmation` / `last_citations` / `run_stream`；`chat.py` 用 `getattr` 消费，切换引擎不改路由层 |
| **工具总数还很小** | 6 个：`kb_search` + 5 个 todo |
| **双引擎有维护契约** | AGENTS §2：改动其一必须跑两套测试 |

> 一句话：**“多智能体”这件事，本项目的门槛不是“能不能做”，而是“要不要把它变成主干”**——骨架已经在跑了。

## 2. 核心抉择：单智能体 vs 多智能体

| 维度 | 单智能体（+工具渐进披露 + Agent-as-Tool） | 多智能体（supervisor + 子 Agent） |
|---|---|---|
| LLM 调用/轮 | 1-2 次 | **2-3 次**（路由 + 子 agent + 汇总） |
| 失败面 | 无路由步骤 | **多一层路由失败点**（判错则整轮错） |
| 调试 | 一条 trajectory | 跨节点，链路更长 |
| 上下文隔离 | 弱（全塞一个窗口） | **强**（子 agent 独立上下文） |
| 工具爆炸（MCP 接入后） | 靠“渐进披露”收窄 | 靠“子 agent 分片”，但要防 `None`（全量）节点 |
| 职责分离/可讲性 | 一般 | **强**（面试演示价值高） |
| 实现成本 | 低 | 中（已有骨架，不算从零） |

### 2.1 反方论点（讨论中我提出的，如实保留）

1. **个人助手的负载是串行且带状态的**（做一件事 → 记住 → 跟进），不是“多路独立可并行”，多智能体的天然优势用不满；
2. **多智能体治的是“工具膨胀 + 上下文污染”，却引入“路由”这个新病源**——而路由恰恰是最难测、最容易整轮出错的一层；
3. `_keyword_route()` 的存在就是**路由脆弱性的自证**；
4. `tools_agent: None` = **全量工具**：等 MCP 接进来、工具涨到几十个，这个节点的 prompt 会最先爆。

### 2.2 正方论点（最终采纳）

1. **目标含“面试演示”**：多智能体（尤其 LangGraph）是可直接演示、可讲的关键词与结构；
2. **骨架已存在且接口层平权**：不需要重写路由层/记忆/HITL/引用/流式，改造成本远低于新建；
3. **Persona 价值**：能拿出“两套引擎 + 同一套工具抽象 + 对照数据”，比“我用了多智能体”更有说服力；
4. 反方论点的代价**可控**（见 §4 缓解措施），而收益（演示 + 结构清晰）是确定的。

### 2.3 结论

**选多智能体（乙方案）。** 关键理由一句话：

> 这不是“选哪个理论上更好”，而是“**在我明确知道代价的前提下，选了收益更确定的那条**”——因为我的判据是面试演示 + 个人日用，而不是大规模生产。

## 3. 本次讨论暴露的关键问题（真实记录）

> 这一节是本文最有价值的部分：**问题 → 结论 → 证据**。

| # | 问题 | 结论 / 证据 |
|---|---|---|
| Q1 | Agent 主动性怎么落地？ | 载体=**基金盯盘**（批次 P）；⚠️ 场外基金净值**晚间才公布**，“15:30 播报”拿到的是昨日数据 → 定 21:30 |
| Q2 | 双引擎成本真的是 2× 吗？ | **不是。我最初的判断是错的**：新增能力**做成工具**时成本 ≈ 0（共用 `global_registry`，只需在 `AGENT_TOOLS` 挂名字）；**只有改引擎本身**（循环语义/HITL/流式）才付 2× |
| Q3 | 多智能体解决的到底是什么病？ | 治“工具膨胀 + 上下文污染”，但引入“路由失败点”；**收益被高估**，除非子任务真正独立 |
| Q4 | 路由层有多脆？ | `_keyword_route()` 兜底即证据；多一层路由 = 多一个整轮失败面 |
| Q5 | MCP 接入后会先崩在哪？ | `tools_agent: None`（全量工具）——工具数上升时 prompt 最先爆 |
| Q6 | 确定性任务该不该进 agent？ | **不该**：盯盘取数/算账/播报走 `jobs` + 领域工具，**不经 LLM**（省 token、可对账、可断言） |
| Q7 | 子 agent 什么时候真值？ | 仅当**上下文会被中间产物撑爆**时：1 深度研究（多源+交叉验证）2 长文写作/报告 |

### 3.1 顺带纠正的一个“伪结论”

讨论中曾把这套双引擎称为“头号债务”。**经代码核查修正**：在“面试演示”目标下它是**资产**（可对照、可讲取舍）；它的真实成本边界是“改引擎才 2×”。

> 面试可讲点：**“我用代码核查推翻了自己的直觉判断”** —— 这比任何架构名词都值钱。

## 4. 最终决策与代价

### 4.1 决策

| 项 | 决定 |
|---|---|
| Agent 形态 | **多智能体**（supervisor + 专项子 Agent） |
| 主干路径（日用） | **LangGraph 多智能体**（U1-a；骨架现成、接口层平权） |
| 对照路径 | 手写 `Orchestrator` 降为**对照/回退**，功能冻结，只做演示与对照评测 |
| 确定性任务 | **不进 agent**：走 `jobs`（J1）+ 领域工具 |
| 子 Agent 引入时机 | 仅“上下文隔离有真价值”时（深度研究、长文写作）——**不为了好看而拆** |

### 4.2 接受的代价（明确知道）

1. token/延迟 ≈ 2-3×（个人规模可承受）；
2. 多一层路由失败面；
3. 调试链路更长（需跨节点追踪）。

### 4.3 缓解措施（代价换来的风控）

| 代价 | 缓解 |
|---|---|
| 路由判错整轮错 | **保留关键词兜底** + 路由结果落 trajectory（可评测、可回归） |
| `tools_agent: None` 会爆 | 改**显式工具白名单**，随能力增长分批披露 |
| 调试链路长 | 把 `plan → 节点 → 工具 → 结果` 全量落进 `Message.extra`（**可观测是这次改造的硬要求**） |
| 成本不透明 | 用同一批 golden 问题跑**两引擎对照**（token/延迟/准确率），把数据变成演示资产 |

## 6. 面试话术与追问应对

**一段话版本：**

> “我实现了两套 Agent 引擎、共用一套工具注册表：手写 ReAct 和 LangGraph 多智能体，接口层平权（HITL、引用、流式都有）。我评估过：多智能体会让 token 涨到 2-3 倍、多一层路由失败点，而我的任务大多是串行短任务，理论上单智能体更划算。但我的目标是**演示 + 日用**，而且骨架已经存在、改造成本低于新建，所以我选多智能体作为主干，同时把确定性任务（基金盯盘播报）**完全排除在 LLM 之外**，并用同一批 golden 问题做两引擎对照数据。”

**可能的追问：**

| 追问 | 应对 |
|---|---|
| 为什么要多智能体？ | 上下文隔离 + 职责分离 + 演示价值；并主动承认反方论点，说明我**知道代价并接受** |
| token 涨了怎么办？ | 三层：子 agent 工具白名单（防 `None` 全量）、确定性任务不进 agent、对照评测量化 |
| 怎么保证路由不判错？ | 关键词兜底 + 路由落 trajectory + 回归用例；**承认这是多智能体的固有代价** |
| 什么时候会退回单智能体？ | 若对照数据显示准确率无提升且延迟不可接受 → 主干退回单 agent + Agent-as-Tool（`base.py` 已留该扩展点） |
| 跟盯盘有什么关系？ | 盯盘是“确定性管道 + 领域工具”，**Agent 只负责对话里的查询**——这条边界是我刻意划的 |

## 7. 与批次 P（基金盯盘 + MCP）的一致性

盯盘批次的三条决策，正是本次 Agent 哲学的具体化：

| 批次 P 决策 | 与本文的关系 |
|---|---|
| P0.3 行情走 `ToolRegistry`，不进 RAG | “取数用代码，说话才用 LLM” |

> 统一原则：**能用确定性代码解决的，绝不交给 Agent；Agent 只做“需要判断”的部分。**
