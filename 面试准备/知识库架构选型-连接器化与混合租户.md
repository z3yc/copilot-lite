## 1. 核心抉择：直接读 Obsidian vs 索引进本系统

### 1.1 两条路的本质
| 维度 | 直连（读文件 / Obsidian 插件 / MCP） | 索引（解析→分块→向量，本系统） |
|---|---|---|
| 单一事实源 | vault（天然最新） | vault 仍是事实源，本系统是**派生索引（read model）** |
| 检索 | 文件名/字面 grep | **BM25 + 向量 + RRF + Rerank**，命中口语化提问 |
| 跨来源 | 只能 Obsidian | Obsidian + PDF/Word/网页/代码 **统一检索** |
| 部署 | 仅本机（云后端摸不到本机盘） | **本地 + 云端 + 多端**（zip/受管副本） |
| 权限/多租户 | 基本没有 | 可做租户/文档级 ACL |
| Agent 集成 | 需另造工具 | 复用 ToolRegistry / 记忆 / 引用 / HITL |
| 写回 | Local REST API / MCP 原生支持 | 自造编辑器（不划算） |
| 成本 | 零索引 | 一次嵌入 + 同步维护 |

### 1.2 结论与理由
- **索引作为主干**：企业不会有"所有人把笔记放在本机 Obsidian 等你直读"；企业要的是**多来源 + 权限 + 审计 + 成本**。索引提供统一检索与治理入口。
- **直连降级为连接器/增强**：本地小 vault 可直读（省索引成本），但它是"一种来源"，不是系统本身。
- **写回不自己造**：交给 Obsidian Local REST API / MCP，**编辑在 Obsidian，检索在平台**（CQRS/读写分离）。
- 面试话术："我把 vault 当**单一事实源**，系统只建**可重建的派生索引**；直连是其中一个连接器的能力，不是架构主干。"

> 判据：仅"单机 + 单源 + 无多用户/云端"时，直连更对；一旦涉及**跨源/云端/多端/权限**，索引就有价值。

## 2. 连接器化（Connector）——企业落地的关键 seam

### 2.1 为什么
- 企业知识来源是**多样且不断新增**的：Obsidian / S3 / SharePoint / Confluence / Git / 数据库。
- 若把"来源"写进核心检索/权限逻辑，每接一个来源都要改核心 → 违背开闭原则。
- 抽象：**外部源 → 连接器 → 统一 `documents/chunks`**，核心只认统一模型。

### 2.2 设计
```
SourceConnector(name, create_space, import_archive, sync)
  └── ObsidianConnector（当前实现：本地路径 / zip）
  └── (未来) S3Connector / SharePointConnector / ConfluenceConnector
检索 / ACL / Agent 不感知具体来源
```

### 2.3 不选什么 / 取舍
- **不为抽象而抽象**：只抽"真会多实现"的边界（来源），不提前拆微服务。
- **不复制外部文件**（本地路径为只读扫描）：索引是派生数据，不制造第二事实源。
- 面试话术："连接器是**开闭原则**的落地：加来源=加实现+注册，不动检索核心。"

## 3. 混合租户模型（公司租户 + 部门 workspace + 多租户 SaaS）

用户选择"**混合模式**"：既要支持"一家公司一个租户、部门/项目做 workspace"，也要支持 SaaS 多租户各自独立。

### 3.1 模型
```
Tenant（组织/公司；隔离边界，SaaS 里=一个客户）
  └── Workspace（部门/项目/团队；知识空间，1 个 Obsidian vault = 1 workspace）
        └── Membership(user ↔ workspace, role: owner/admin/member/viewer)
Documents/Chunks 携带 tenant_id + workspace_id (+ acl)
```

### 3.2 检索过滤链（企业命门）
```
query → 过滤 tenant_id → 过滤"当前用户可访问的 workspace 集合" → 过滤 document.acl → 混合检索
```
- **演示模式**：默认单租户 + 默认 workspace，行为与现在一致（零感知）。
- **企业模式**：多租户 + 多 workspace + 角色；`WIKI_ALLOW_LOCAL_PATH=false`、ACL 生效。

### 3.3 为什么不是简单加 `user_id` 就够
- 企业要求**共享知识**（部门/项目级），不只是个人私有；
- 要求**跨用户检索同一 workspace**，但**不能越权**；
- 要求**租户级成本/审计/数据驻留**，需要 tenant 边界。

### 3.4 为什么不做成"每个用户一套索引副本"
- 存储/嵌入成本 ×N；共享知识无法复用；权限更新难以一致。
- 正确做法：**一份索引 + 过滤链**（tenant/workspace/ACL），这也是主流企业 RAG 的做法。

### 3.5 取舍
- 不引入完整 RBAC/ABAC 引擎与图数据库：先用"tenant + workspace + 角色 + 文档 ACL"覆盖 90% 场景；
- 复杂度集中在**过滤函数**（检索/向量/BM25 三路都要带过滤），而非散落各处。

面试话术："租户模型用**混合模式**：tenant 是隔离边界，workspace 是协作/知识边界；权限通过**统一的检索过滤链**穿透到向量与 BM25 两路，而不是只在 API 层鉴权。"

## 4. 配套工程选型（本项目已做）

| 事项 | 选择 | 为什么 |
|---|---|---|
| 批量/长耗时导入 | 先请求内同步，**规划改后台任务 + 进度** | 大 vault 不阻塞 HTTP；企业要吞吐/重试 |
| 嵌入模型加载 | **持久缓存目录 + 离线优先(`local_files_only`) + 启动预热** | fastembed 默认落 `%TEMP%` 且每次联网校验，首次慢到 50s+；实测优化后 0.13s |
| 双链图谱可视化 | `react-force-graph-2d`（现成库） | 快速出效果、不引 three.js（见另一篇复盘） |
| 本体（Ontology） | **不做完整本体**，M4 可选"轻量本体（类型化链接）" | 个人/一般企业到不了完整本体的收益拐点（见另一篇复盘） |

## 5. 企业落地路线（"留口优先，不破坏 demo"）

| 阶段 | 动作 | 企业价值 | Demo 价值 |
|---|---|---|---|
| 现在 | ✅ 连接器化收口（已完成） | 多来源可扩展 | 架构叙事强 |
| 下一步 | 租户/workspace 字段 + ACL 检索过滤（混合模型） | 上线硬门槛 | 讲透"隔离穿透" |
| 之后 | 异步摄取（Job 表 + 队列）、可观测（OTel + 按租户成本） | 可运营 | 工程化加分 |
| 之后 | 评测进 CI（recall@K / faithfulness 阈值） | 质量门槛 | 已有脚本 |
| 远期 | 审计日志、软删除/可删、Secret Manager、K8s/HA | 合规与规模 | 按需 |

> 原则：**单体模块化（Modular Monolith） + 配置驱动 + 基础设施可替换**；不到压力点不拆微服务。

## 6. 高频追问速答

- **"为什么不直接读 Obsidian？"** → 单机单源可以直读；企业要跨源/权限/云端，故以**索引为派生缓存**、直连为连接器能力。
- **"为什么抽象连接器？"** → 企业来源多样且会新增；连接器把"来源差异"隔离在核心之外（开闭原则）。
- **"混合租户怎么隔离？"** → tenant 隔离边界 + workspace 协作边界 + 角色 + 文档 ACL，统一在**检索过滤链**（向量 + BM25 + 引用）里穿透。
- **"为什么不做每用户索引副本？"** → 成本 ×N、共享难、权限难一致；一份索引 + 过滤链更合理。
- **"嵌入为什么曾很慢？"** → 缓存默认在 `%TEMP%` 且联网校验；改为持久目录 + 离线优先 + 预热。
